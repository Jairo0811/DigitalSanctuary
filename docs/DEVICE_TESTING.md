# Device Testing Strategy

Digital Sanctuary v1.0.1 is currently a native Android application. This guide defines how to test the current Android build and how the project should evolve before running on iPhone.

## Android — current supported platform

### GitHub Actions artifact

The `Android CI` workflow builds a debug APK and uploads it as an artifact named:

`digital-sanctuary-v1.0.1-debug-apk`

The workflow can also be started manually with `workflow_dispatch`.

### Installation

1. Open the latest successful `Android CI` run in GitHub Actions.
2. Download `digital-sanctuary-v1.0.1-debug-apk` from the Artifacts section.
3. Extract the ZIP generated by GitHub.
4. Copy `app-debug.apk` to the Android device.
5. Allow installation from the selected browser/file-manager source if Android requests it.
6. Install the APK.

For development through Android Studio, connect a physical Android device with USB debugging enabled and run the `app` configuration.

### Minimum smoke-test checklist

- Application launches and shows the Digital Sanctuary identity.
- Library loads seeded/local data.
- Book CRUD works.
- EPUB import opens and persists access after relaunch.
- PDF import opens and renders pages.
- Reader position and progress survive relaunch.
- Bookmarks survive relaunch.
- Notes can be created from Reader.
- Knowledge Hub search finds books and annotations.
- Tags and knowledge links persist.
- Markdown export opens Android Share Sheet.
- Gemini actions fail gracefully when neither `AI_PROXY_URL` nor a debug key is configured.
- Gemini actions work through the configured proxy in production-like testing.
- AI HTTP failures return a controlled error instead of crashing the application.
- A stalled AI endpoint respects the configured OkHttp timeouts.
- App data is not offered to Android Auto Backup or device-transfer backup rules.

## iPhone / iOS — not directly installable yet

The Android APK cannot run on iPhone. The current UI and Android platform integrations use Android APIs such as Jetpack Compose, Room, Storage Access Framework and `PdfRenderer`.

The recommended professional evolution is **Kotlin Multiplatform (KMP)** rather than creating an unrelated second codebase.

### Target architecture

```text
DigitalSanctuary
├── shared/
│   ├── domain
│   ├── application
│   ├── repository contracts
│   ├── knowledge models
│   ├── AI contracts
│   └── shared business rules
├── androidApp/
│   ├── Jetpack Compose
│   ├── Android document picker
│   ├── Android PDF renderer
│   └── Android persistence adapter
└── iosApp/
    ├── SwiftUI or Compose Multiplatform
    ├── UIDocumentPickerViewController
    ├── PDFKit
    └── iOS persistence adapter
```

### What should be shared

- Book and reading-state models.
- Reader location/progress rules.
- Bookmark and annotation models.
- Knowledge-link logic.
- Search/filter rules.
- Repository interfaces.
- Gemini/AI use cases and request policies.

### What remains platform-specific

| Capability | Android | iOS |
|---|---|---|
| UI | Jetpack Compose | SwiftUI or Compose Multiplatform |
| File picker | Storage Access Framework | UIDocumentPickerViewController |
| PDF | PdfRenderer | PDFKit |
| Local database | Room/SQLite | KMP-compatible SQLite adapter |
| Share | Android Sharesheet | UIActivityViewController |
| Secure secrets | Android build/runtime config | Keychain/runtime backend config |

### Recommended migration sequence

1. Keep Android v1.0.1 stable.
2. Extract pure Kotlin models and business rules into `shared`.
3. Move repository contracts/use cases to `shared`.
4. Replace direct Room dependencies in shared logic with interfaces.
5. Add multiplatform SQLite persistence.
6. Implement iOS document import and PDFKit adapter.
7. Build the iOS UI.
8. Run shared unit tests on Android/JVM and iOS targets.
9. Test on a physical iPhone through Xcode.
10. Later distribute through TestFlight.

## Release-testing policy

Debug APKs are suitable for internal Android testing only. A public Android release should use a signed release APK/AAB. iOS distribution should use Xcode signing and TestFlight; no Android artifact should be treated as an iOS package.
